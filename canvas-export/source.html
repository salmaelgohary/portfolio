Overview

Trax helps construction professionals find and verify building code requirements digitally.

Trax digitizes 80+ Canadian building codes, helping architects, engineers, and construction professionals quickly find the requirements they need.

Copilot is Trax’s AI assistant for searching and understanding those codes. As Trax moved toward an AI-powered compliance platform, Copilot became central to the product.

Problem

Copilot was becoming central to Trax, but users had to dig to find it.

Users had to navigate through three steps to find Copilot, and its entry point looked almost identical to Trax’s regular keyword search.

Copilot needed to become a more prominent part of the platform.

As Trax leaned further into AI, we had an opportunity to make Copilot a more visible and recognizable part of the platform.

Solution

We made Copilot easier to find, easier to use, and easier to trust.

The new Copilot experience makes it easier to access AI-powered code search, refine questions with context, and verify answers against source documents.

One-click access from anywhere in Trax

Copilot moved into the top-level navigation, so users can start a question from any screen instead of digging three steps down.

Persistent filters for more focused questions

Filters stay applied across questions as editable pills, so users can narrow to a codebook or municipality once and keep refining.

Inline citations for easy source verification

Citations open a reference panel beside the answer, so users verify against the source without leaving the conversation.

Research

I started by looking at where Copilot was falling short.

I combined heuristic evaluation, existing user feedback, and feature requests to understand where users were running into friction.

Five key problems

Copilot was difficult to discover within the existing navigation.
Its entry point looked too similar to regular search.
Filters reset between questions.
Answers lacked clear, accessible citations.
No clear way to start a new question without losing context.

Better examples of what Copilot could help with.
A way to compare answers across codebooks and municipalities.
More control over which sources Copilot used.
A way to refine an answer without starting over.
More confidence that answers reflected the latest applicable code.
Competitor research

Competitors made it difficult to verify AI responses against source documents.

Most competitors relied on long responses and scattered references, forcing users to scroll through the response or leave the conversation to find the supporting source.

This gave us an opportunity to make source verification faster by keeping relevant code references close to the answer.

Design process

I mapped the existing flow and explored ways to improve it.

{{ flowGlyph }}

I mapped the existing Copilot experience to identify where users were running into friction, then explored different ways to improve the flow. The biggest gaps appeared around entering Copilot, refining a question, and verifying the response.

A technical constraint changed the direction.

I explored using color to distinguish different codebooks (e.g. fire and building codes). After reviewing the idea with development, I learned the backend didn’t currently support this distinction, so we moved it out of scope.

Design decisions

How should Copilot introduce its capabilities?

Show everything upfrontUsers see all suggested prompts when they open Copilot. This made capabilities immediately visible, but presented too many options at once and made the starting point feel crowded.
Progressive disclosureUsers see a focused starting point and can open prompt categories when they want more guidance.
We chose progressive disclosure to avoid overwhelming users with too many options while still giving them a clear way to explore what Copilot could do.

How should filters be displayed?

Box-style filtersUsers select filters from box-style controls that show their selections inside. This kept the search bar height consistent, but was less scalable as users selected multiple filters.
Pill-style filtersSelected filters appear as pills below the filter controls, making them easy to scan, edit, and remove from the conversation.
We chose pill-style filters because they were easier to scan and could scale as more filter types were added.

How should filter colors be used?

Different colorsEach filter type uses a different color to make categories visually distinct. This made types easier to distinguish, but the colors competed for attention and could be read as carrying meaning.
Similar colorsFilter pills use similar shades to create a more consistent visual system.
We chose similar colors to keep the filters visually consistent and less distracting, while grouping them by type to maintain distinction.

How should users verify an AI-generated response?

Reference panelWe redesigned the citations as a reference panel so users could verify an answer without losing their place in the conversation. The narrower answer area was worth the tradeoff because verification stayed in the same workflow.

How should new questions work in the Standard tier?

Override the current chatNew questions replace the current conversation, reducing clicks and matching the Pro experience. Faster, but could make Standard users expect conversations to carry context and be saved.
Start a new chatEach new question starts a separate conversation and shows suggested questions to help users get started.
We chose start a new chat because Standard users didn’t have persistent chat history. Keeping each question separate made the product’s limitations clearer and avoided implying that context would carry over when it wouldn’t.

We created a more discoverable and trustworthy Copilot experience.

The redesigned experience makes Copilot accessible from anywhere in Trax, helps users refine questions with persistent filters, and lets them verify answers through inline citations.

Bring developers into the conversation early to understand technical constraints before committing to a direction.

Scope to the minimum users actually need

Keeping the scope focused helped us prioritize the problems we could meaningfully solve within the project.

Test Copilot in real code research workflows

Observe architects, engineers, and construction professionals using Copilot to answer real compliance questions, focusing on whether users can find the right sources, refine their questions, and confidently validate the response.

Expand the filtering system

As more code types and project contexts are added, revisit the filter structure to make sure users can still scan and adjust their context without adding complexity.

Overview

How can smart technology help people stop losing sleep over uncomfortable temperatures?

As the sole product designer, I explored, designed, and validated an automated overnight climate control experience designed to help people maintain better sleep throughout the night.

Research & discovery

Looking into overnight body temperature changes, sleep disruptions, and where traditional thermostats fall short.

Prototyping & testing

Exploring a wide range of ideas and rapidly testing concepts with users.

Iterating with feedback

Refining body tracking and device interaction flows based on real user testing.

Problem

Fixing sleep disruptions shouldn't have to be a manual chore.

Poor sleep affects mood, focus, and performance. Too often, it happens simply because a room gets too hot or cold overnight.

Today, there is no easy way to understand how temperature affects sleep throughout the night. When people wake up freezing or overheating at 3:00 AM, fixing it is completely manual — get out of bed, change the controls, and try to fall back asleep. These frustrations became the starting point for SleepWell.

How might we regulate a person's sleep environment to maintain a comfortable temperature throughout the night?

Opportunity

Connecting body temperature to the environment to make sleep regulation proactive

Sleep trackers and smart thermostats operate separately today. Trackers tell people how their sleep was after the fact, while thermostats rely on fixed temperatures and schedules. Connecting the two creates a closed-loop system that can respond to the sleeper instead of making them respond to their environment.

Preventive intervention

SleepWell responds to changes in body temperature as they happen and adjusts the environment before discomfort wakes someone up.

A closed-loop experience

Connecting the wearable, climate control, and app creates one system that can sense, respond, and learn throughout the night.

Personalized sleep patterns

Over time, body temperature and sleep data reveal patterns unique to each person, moving beyond a fixed temperature setting.

Solution

An automated system that monitors and regulates room temperature overnight

SleepWell brings together a smart wristband, a fan, and an app connected over Bluetooth. The wristband tracks body temperature throughout the night and sends that data to the fan, which adjusts the room temperature to keep the sleeper near their preferred range.

The app logs the data overnight so people can review their sleep patterns and insights when they wake up.

Core flows

Log sleep quality

A single labelled action at the end of the night that feeds personalized sleep insights.

Set a desired nightly body temperature

The temperature target is the home screen — one clear value to adjust.

Explore sleep insights

Insight cards expand to explain patterns over time, not just last night.

Review nightly results

Each morning connects the night’s temperature data to smart recommendations.

100% increasein insight discovery — no user expanded an insight before testing; all 5 did after

Talking to students and athletes dealing with constant temperature swings

The research started with high school students balancing heavy sports and extracurricular schedules. They were expected to get eight hours of sleep while often averaging only five to six.

Across these groups, the same three pain points kept coming up: maintaining a comfortable room temperature was a constant struggle, low energy affected the next day, and there was no clear way to understand when a sleep disruption actually happened.

Competitor research

Looking at what already exists in smart thermostats and sleep apps

A quick look at existing products revealed familiar patterns: simple icons, clean home screens, and temperature controls using smooth visual gradients.

Design process

Kicking things off with Crazy 8s to test eight different layouts

One direction stood out: a vertical temperature slider paired with a clean layout and subtle icons for secondary features. It built on familiar patterns from the competitive review while giving temperature control the most visual weight.

Storyboarding revealed that sleep logging could be the product's long-term value.

The wireframes focused on controlling temperature, but storyboarding revealed a bigger opportunity. Logging sleep data over time gives the app a reason to stay useful beyond a single night — seeing how body temperature connects to sleep quality helps people understand what works for them.

Turning the concept into testable flows

Mid-fidelity wireframes brought the core experience together and were ready to test with five users.

Putting prototypes in front of real users to catch friction early

Uncovering why students miss buses through surveys and mapping key intervention points across the commute.

Turning the strongest direction into a focused, testable product experience.

Problem

Transit apps tell you when the bus arrives. They do not tell you when to leave.

University students relying on GO Transit frequently miss buses even after checking transit apps. Delays, slow updates, and packed academic schedules make commuting stressful.

Existing transit apps show when a bus is scheduled to arrive, but they don't account for the things that actually affect when someone needs to leave — traffic, weather, walking time, or a personal schedule.

How can we help students leave at the right time and make their commute more reliable?

GO Smart leads with when to leave, not when the bus arrives.
Opportunity

Personal context as the core of GO Transit's student experience.

Transit apps already make routes, schedules, and live updates easy to access. The bigger opportunity is to understand the person behind the trip. For students, when to leave depends on their classes, routines, and what is happening around them.

Personalization

Understand each rider's routines, priorities, and needs instead of treating every trip the same.

Daily relevance

Become useful beyond the moment someone checks a bus schedule, creating a reason to return every day.

Stronger rider loyalty

Build a relationship around helping students get through their day, not just getting them from one place to another.

Solution

An AI-powered assistant that adapts to the commute in real time

GO Smart combines real-world conditions with a student's schedule and habits. Instead of simply displaying a bus schedule, it tells students when to leave and why.

Behavioral learning

GO Smart learns personal patterns, such as consistently leaving the house five minutes late, and adjusts reminders to help students stay on schedule.

Real-time conditions

Live traffic, weather, and travel modes dynamically update departure times as conditions change.

Calendar integration

The app connects to class and personal calendars to automatically build a weekly bus plan around a student's schedule.

High-visibility notifications

Lock-screen alerts and auditory cues help students notice important departure changes even when they're busy.

The departure time moves as conditions change, rather than staying fixed to the schedule.
Research

Knowing when to leave requires too much effort.

Students have to piece together information from their transit app, weather, schedule, and live conditions to figure out when they should leave. Initial discussions with university students uncovered four key pain points.

Transit updates were delayed or inaccurate

Students could not always rely on the information shown in the app to reflect what was happening on the road.

Changes were easy to miss

When a bus was running early or late, students often had to actively check the route to know something had changed.

External conditions affected departure time

Traffic, weather, and walking time could all change how early a student needed to leave, but these factors were never considered together.

Personal schedules made every commute different

Changing classes and other commitments meant students had to figure out their departure time around a different schedule each day.

Journey mapping

We mapped the student commute from planning the trip to boarding the bus to understand where students were spending the most effort and where there was an opportunity to intervene.

Key insight: the information students need already exists, but they have to connect it themselves.

Design process

A proactive commute experience, built around the student's day.

I mapped the product experience before designing individual screens, making sure the key pieces worked together from planning the week to getting out the door. The core flow connects calendar-based planning, real-time conditions, and departure reminders into one experience.

Flows came before screens, so the features had to connect end to end first.

One early concept explored letting riders signal bus drivers when they were running late. While interesting, it introduced too many questions around driver workflows and feasibility. This pushed us to focus on what the passenger could actually control: knowing when to leave.

The weekly plan is generated automatically, so nobody has to re-plan every week.

Overview

Building a repeatable AI content pipeline for a wellness app at scale

U4RIA is a lifestyle app that uses AI to generate meditations, music, recipes, and daily affirmations at scale. While AI makes asset creation fast, keeping a consistent brand look and feel across hundreds of pieces of content is a major hurdle. Without a structured workflow, every single output requires the same manual fixing as starting from scratch.

I took lead on designing and running the AI content pipeline, turning brand intent into a reliable system that produced every piece of content the app shipped with.

The challenge

Maintaining consistency at volume is hard

Generating one-and-done AI assets is straightforward, but keeping a large library of various types of content consistent in visuals and tone is not.

Without a system, the AI outputs drift all over the place and require constant revisions. To solve this, I decided to treat AI like a production line — writing clear instructions, testing what worked best, and turning those successful formulas into steps the team could repeat.

The pipeline

Five stages that made AI outputs reliable at volume

Define intent first

Before opening any tool, I established the communication goal, emotional tone, and format requirements to anchor every output in the core brand direction.

Translate intent into structure

I converted creative direction into structured prompts for Midjourney, Suno, and Kling AI, iterating on the language to keep results steady and predictable.

Generate and evaluate

I produced multiple variations per prompt and selected the ones that hit the right balance of brand alignment, clarity, and quality.

Refine for platform

I brought generated assets into Canva to polish composition, pacing, typography, and platform-specific sizing for Instagram, TikTok, and in-app placements.

Manage at scale

I built an organized tracking system in Airtable to log prompt formulas, ensuring asset sets remained cohesive while leaving room for intentional variety.

Final content

Social media posts

I made base visuals in Midjourney, then brought them into Canva to clean up the text, spacing, and brand frames — keeping the text easy to read and matching U4RIA's visual style.

Recipe images

I generated realistic food photos for grain bowls, smoothies, and light dinners, and built reusable prompt templates in Airtable so the team could make new recipe photos later without breaking the style.

App splash screens

I designed the starting and ending screens by hand in Canva for full control over layout, then used Kling AI to generate only the transition between them.

Audio tracks

I made guided affirmations and background music in Suno, testing voice tone, speed, and background sounds to match different kinds of mindfulness exercises.

Short-form videos

I generated scene images in Midjourney, turned them into clips with Kling AI, and stitched them into loops in Canva for TikTok and Reels.

Outcomes
38% reductionin revision work — setting goals early and reusing tracked prompts meant far less back and forth
Reflection

What I learned

Specificity is a design constraint

AI works best when prompts are clear boundaries instead of vague suggestions. Defining the mood, inputs, and rules up front produced fewer stray variants and moved everything faster.

AI is an execution layer, not a decision maker

I learned to make creative and strategic decisions before involving AI. Treating it as a production tool rather than a source of direction resulted in higher-quality, more intentional outputs.

Users weren't sure why they should install AI Bundle or what they could do with it. The number of tools and technical terminology felt intimidating, causing some users to drop off before installing anything. Primary goals: discover AI tools, understand what they do, identify the right software, install software.

Experienced users knew what they needed, but setup was tedious.

These users came in with specific software in mind and wanted to get their workflows running without manually managing software compatibility. Primary tasks: install software, manage installation locations, maintain compatible versions.

How might we make setup more approachable without taking away control from experienced users?

I mapped the journey from discovering AI Bundle and Playbooks to installing the software needed for each task. The approach was to give beginners more context before introducing the software, while keeping a faster path for experienced users.

Models were part of the original scope, but that changed mid-project.

Midway through the project, product management removed Models from scope due to implementation timelines and model file sizes. I removed the model cards and related setup states from the release and reworked the remaining experience.

Technical constraints

The experience looked simple, but the installation system was anything but.

I worked with engineering to map the edge cases behind installation, including dependencies, storage, installation paths, cancellation, and partial failures.

One global install path would have been simpler, but it wasn't how the system worked.

We initially designed one global install path for the installation overlay. After working with engineering, we learned that applications could install into different folders, while some had fixed locations — so how might we expose that flexibility without making installation feel complicated?

Exploration 1 — global drive selector

We first changed the global install path to a drive selector. This gave users a way to switch drives when storage was limited, but did not show where each application would actually install.

Exploration 2 — show every install path

We then showed the install path for every application. This gave users visibility into where each app would go, but added too much information to an already dense overlay.

Exploration 3 — hide paths by default

We moved paths behind a control so users could focus first on version and size while keeping paths available when they needed more context.

Exploration 4 — surface locked locations

Some applications had fixed locations, so we added a tag to surface those without requiring users to expand the install paths. This made the expanded state too crowded, so we simplified the layout to keep path, version, and size from competing for space.

Where we landed

The final overlay keeps version and size focused while making install locations available when users need them. The tradeoff was more flexibility at the cost of some added complexity, but the final model matched how installations actually worked.

Dependencies should be understandable, not another thing to manage.

Some applications require other components to work — PyTorch requires Python, for example.

Scannable dependencies

Individual installs use app icons so users can quickly see what will be installed alongside the selected application.

Locked required dependencies

In the installation overlay, required dependencies are locked, with a hover explanation showing why they are needed.

Storage should inform the decision.

Available space can differ by drive, and some applications can only install to specific locations. I surfaced required and available space where it affected the decision and kept location controls available where supported.

Recovery shouldn't undo completed work.

If one application fails or is cancelled, users shouldn't have to start over. Completed applications remain installed, failed items can be retried, and cancelled items return to an installable state.

Final flow

A simpler way to get from an AI goal to a working setup.

Playbooks gives beginners a task-first entry point. Software keeps direct management available for experienced users. Sync handles version alignment without asking users to manage compatibility themselves.

Reflection

What I learned

Bring engineering into edge cases early.

Some storage and installation constraints surfaced later in the process. Bringing engineering into these conversations earlier would have helped me account for them sooner.

Stay detached from your designs.

When the Models feature was removed mid-sprint, I had to quickly rethink parts of the experience. In a fast-moving environment, designs need to change with the product.

Technical constraints are part of the design.

The final experience depended on complex rules around paths, dependencies, storage, and installation states. Working through those constraints helped me turn system behavior into simple user decisions.
